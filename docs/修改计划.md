# 满改平台 App 原型优化修改计划

> 基于《用户、服务商端App原型优化修改意见(宋总)》文档整理，以**蓝色字体意见为核心**，结合各页面问题与修改建议，形成以下执行计划。

---

## 一、战略层定位修正（蓝色意见优先）

### 1.1 平台定位明确
- **核心意见**：当前平台不是服务平台，主体靠**授权品牌商品 + 金融**做业务。
- **执行动作**：
  - 弱化服务撮合能力，不在商城层面做服务交易闭环。
  - 服务商仅作为**推荐和事务状态跟进**角色，不直接承担服务交易主体责任。
  - 聊天过程必须通过平台，确保平台对交易的把控。

### 1.2 订单状态机制统一
- **核心意见**：状态机制需要统一，平台、服务商、用户三端要根据不同阶段定义可显示名称。
- **执行动作**：
  - 建立统一状态机，定义完整订单生命周期。
  - **自提订单**：下单中 → 已下单 → 已发货 → 已签收
  - **服务订单**：下单中 → 已下单 → 已发货 → 到场服务 → 施工中 → 待验收 → 完成
  - 为三端分别映射可见状态名称与可操作动作（用户端、服务商端、平台后台）。

### 1.3 金融授信通用化
- **核心意见**：授信在任何交易中都可以使用。
- **执行动作**：
  - 金融授信入口不局限于特定订单类型，商品订单、服务订单、组合方案订单均支持授信支付。

### 1.4 售后与评价闭环
- **核心意见**：售后验收环节需要增加订单的售后发起和跟进功能；商品销售完毕（已完成状态）增加评价功能。
- **执行动作**：
  - 在订单流程中增加**售后发起**入口（用户端）。
  - 增加**售后跟进**功能，支持用户与服务商双向沟通。
  - 订单完成后（已完成状态）触发**评价功能**。

## 二、用户端 App 修改计划

### 2.1 社区首页
**核心蓝色意见**：
- 卡片信息简要点，可以给发帖人做发帖时提示。
- 帖子内部内容可以做多种链接跳转。

**配套修改**：
| 序号 | 修改项 | 说明 |
|------|--------|------|
| 1 | 内容分类与标签 | 社区内容分为：玩家案例、官方活动、知识科普、商品挂载、门店案例，卡片露出清楚的内容标签。 |
| 2 | Tab 结构优化 | "推荐" 作为社区一级页面主标题 Tab，接搜索/筛选、热门/最新。 |
| 3 | 去掉顶部头像 | 当前无意义，直接移除。 |
| 4 | 发帖按钮悬浮化 | 顶部右侧"新增帖子"与搜索冲突，改为右下角悬浮按钮。 |
| 5 | 卡片字段补充 | 补用户决策字段：车型、改装项目、方案清单数量、关联商品、服务门店/同款案例。 |
| 6 | 主动作差异化 | 不同内容类型对应不同主动作：玩家案例→看清单、官方活动→看商品、知识科普→看适配建议、门店案例→预约同款方案。 |
| 7 | 帖子内多链接跳转 | 帖子正文支持多种链接跳转（商品、方案、门店等）。 |
| 8 | 发帖提示 | 发帖时提示用户填写关键信息，简化卡片展示。 |

---

### 2.2 商城首页
**核心蓝色意见**：
- 商城还要适配游客或未登记车辆用户，未注册车辆以热度/置顶+后发先看排序；注册车辆聚焦相关品牌再叠加热度+后发先看。
- 商城不做服务撮合业务，是靠授权品牌商品+金融做的业务，但可以做服务的推荐以及在订单上的实现。

**配套修改**：
| 序号 | 修改项 | 说明 |
|------|--------|------|
| 1 | 游客模式适配 | 未登录/未登记车辆用户可浏览商城，按热度/时间排序。 |
| 2 | 登录用户排序 | 已注册车辆用户优先展示相关品牌商品，再叠加热度+时间排序。 |
| 3 | 筛选与标签 | 增加"适配我的车、含安装、附近可服务、同车型案例、预计工时"等筛选或标签。 |
| 4 | 商品卡片补充 | 补充安装服务、可服务门店、施工周期、库存/预约状态，体现改装服务型交易特征。 |
| 5 | 服务推荐定位 | 商城不做服务撮合，仅做服务推荐和订单履约状态跟进。 |
| 6 | 推荐方案（可选） | 方案页展示方案构成、适配车型、总价、服务门店和下单步骤。 |

---

### 2.3 爱车页
**核心蓝色意见**：
- 价格仅是商品 + 折扣优惠，服务费是参考价格，不参与交易。

**配套修改**：
| 序号 | 修改项 | 说明 |
|------|--------|------|
| 1 | 配置中心定位 | 爱车页定义为配置中心，说明车辆档案用于车型适配、报价和施工排期。 |
| 2 | 组合方案下单拆分 | 拆成三步：确认车辆与适配性 → 选择门店与预约时间 → 确认报价和服务条款。 |
| 3 | 价格拆分明确 | 商品费用、施工费用（参考价）、门店服务、优惠、预计总价；施工费不参与交易，仅为参考。 |
| 4 | 门店二次确认机制 | 预留门店对施工价格的二次确认机制。 |
| 5 | 车辆卡片交互优化 | "选择车辆"和"新增"放入车辆卡片内，支持左右滑动切换车辆（类似 Banner）。 |

---

### 2.4 消息页

| 4 | 消息分类 | 分为：订单通知、施工进度、验收/售后、系统消息、客服/门店沟通。 |
| 5 | 已读未读功能 | 添加已读未读标识和"全部已读"功能。 |

### 2.5 我的页
**核心蓝色意见**：
- 状态定义：自提（下单中→已下单→已发货→已签收）；服务（下单中→已下单→已发货→到场服务→施工中→待验收→完成）。
- 授信在任何交易都可以使用。

**配套修改**：
| 序号 | 修改项 | 说明 |
|------|--------|------|
| 1 | 订单状态更新 | 按上述定义统一展示自提/服务订单状态。 |
| 2 | 订单类型标识 | 区分商品订单、服务订单、组合方案订单，列表中增加类型标识。 |
| 3 | 入口业务关系梳理 | 电子凭证关联质保/验收单，金融授信关联所有交易，收货地址仅在纯商品配送中出现。 |

## 四、两端联动与共性归纳

### 4.1 统一状态机（核心）
- 建立一套贯穿平台、用户端、服务商端的统一订单状态机。
- 每端根据角色显示不同的状态名称和可执行动作。

### 4.2 消息与业务动作绑定
- 消息分为：系统通知、客户会话、订单动作、售后工单。
- 所有消息必须绑定业务对象（订单/工单），点击可进入详情。

### 4.3 商品-服务-门店关系梳理
- 商品详情同时表达：商品信息、安装服务、可服务门店、预计工期、售后保障。
- 商城定位：商品+金融为主，服务推荐和状态跟进为辅。

### 4.4 车辆档案贯穿全流程
- 爱车页车辆档案用于：商城适配校验、方案报价、施工记录、售后凭证。

### 4.5 验收售后闭环
- 定义完整流程：验收发起 → 用户确认 → 问题反馈 → 返店处理 → 服务商完结 → 平台介入（如有争议）。
- 订单完成后（已完成）触发评价。

## 五、执行优先级建议

| 优先级 | 模块 | 理由 |
|--------|------|------|
| P0 | 战略层定位修正（1.1-1.4） | 影响所有后续页面设计，必须先确定。 |
| P0 | 统一状态机（4.1） | 两端订单、消息、我的页均依赖此基础。 |
| P1 | 用户端-商城首页、商品详情 | 核心业务流，涉及交易转化。 |
| P1 | 用户端-我的页订单状态 | 用户高频页面，状态必须准确。 |
| P1 | 服务商端-订单页 | 服务商核心工作流。 |
| P2 | 用户端-社区首页、帖子详情 | 内容引流，影响用户决策。 |
| P2 | 用户端-爱车页 | 配置中心，影响适配和报价。 |
| P2 | 服务商端-首页工作台 | 提升门店操作效率。 |
| P2 | 两端消息页 | 沟通与业务动作同步。 |
| P3 | 售后评价闭环 | 交易后体验，影响口碑。 |
| P3 | 服务商端-运营、我的 | 经营配置与数据查看。 |

## 六、风险与注意事项

1. **不做 SKU**：商品以销定产，详情页和后台均不需要 SKU 维度管理。
2. **服务费仅为参考**：爱车页、商品详情中的施工费/服务费仅作展示，不参与实际交易金额计算。
3. **服务不做撮合**：商城和服务商端均不做服务交易撮合，只推荐和跟进状态。
4. **授信通用化**：设计和开发时需确保授信支付入口覆盖所有交易类型。
5. **状态名称三端差异**：统一状态机底层一致，但前端展示名称和可执行动作需按角色定制。
